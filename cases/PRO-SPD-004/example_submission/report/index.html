Porting the GPT-2 Medium Speedrun Record to Four GPUs

ABench reference submissionStandard reference for task statement standard v2.1
Abstract

This reference submission is a port, not a new design: it runs the modded-nanogpt GPT-2 Medium track record of 2025-11-12 (Jordan & contributors, 2025) on four instead of eight H100s. The record trains a 16-layer, width-1,024 decoder (454M stored parameters, most of them in four embedding tables and an untied head) with Muon on the hidden matrices (Jordan et al., 2024) and Adam on embeddings, head and scalars (Loshchilov & Hutter, 2019), document-masked FlexAttention (Dong et al., 2024) with a long-short sliding-window pattern (Team & DeepMind, 2024) and value embeddings (Zhou et al., 2024), for 5,960 steps of 524,288 tokens; its log reports a validation loss of 2.9185 after 1,496 s of training on 8 × H100. Here every rank runs two micro-steps per optimizer step so that the global batch, schedule and token budget are the record's, and the step count is raised by 2.3% for margin below the 2.92 target. No run of this port has been executed yet; the operator calibrates it at activation.

1Introduction

Time to a fixed loss rewards both statistical efficiency (fewer tokens to the target) and hardware efficiency (more tokens per second). The anchor fixes the first through compute-optimal scaling (Hoffmann et al., 2022); the speedrun records show that over-training a smaller model with a better optimizer and attention pattern reaches the GPT-2 Medium loss of 2.92 with about 3.1B tokens, two orders of magnitude faster than the original 5.8-hour AdamW baseline of the track.

Items 1–3 of the changes list are borrowed unchanged from the record; items 4–6 are the port.

Changes relative to the anchor. Each item states what this submission does differently and where it is in the code.

  1. Over-training instead of a compute-optimal budget: 454M parameters for about 3.2B tokens (6,100 × 524,288). — train.py: main (--steps)
  2. Muon with Newton–Schulz orthogonalisation and bf16 weights with a separate uint16 mantissa for the hidden matrices; Adam for embeddings, head and scalars; stable-then-linear-decay schedule with a 70% cool-down. — train.py: Muon, update, main
  3. Record architecture: QK-normalised attention with half-truncated rotary embeddings, three value-embedding tables in a 012…012 pattern, U-net skip connections, ReLU² MLP, no attention in layer 7, soft-capped logits, document-masked long-short sliding windows grown with a cubic schedule. — model.py: GPT, CausalSelfAttention, Block, create_blockmasks
  4. Four GPUs with the record's global batch: 8 / W micro-steps per rank, gradients averaged before the Muon and Adam steps. — train.py: train_step, GLOBAL_MICRO
  5. 6,100 steps instead of 5,960 for margin under the target and for the ABench evaluation windows. — train.py: main (--steps default)
  6. Evaluation interface: model(idx) returns soft-capped logits for one window with the final attention window; FlexAttention compiled on its own so the uncompiled module can be evaluated. — model.py: GPT.forward, build_model, flex_attention_compiled

2Related Work

Muon orthogonalises the momentum of each hidden weight matrix with a quintic Newton–Schulz iteration (Jordan et al., 2024) and is the main source of the speedrun's statistical efficiency. FlexAttention compiles attention variants from a mask function and a block mask (Dong et al., 2024); the record uses it to confine attention to documents and to sliding windows, alternating long and short windows as in Gemma 2 (Team & DeepMind, 2024). Value embeddings and value residuals feed token information directly into the attention values (Zhou et al., 2024); rotary embeddings (Su et al., 2021) and the squared ReLU (So et al., 2021) are standard. The record history of the GPT-2 Medium track (Jordan & contributors, 2025) combines these under eight GPUs.

No published record targets four GPUs: halving the GPUs either halves the batch, which changes the optimisation trajectory and the tuned learning rates, or doubles the work per rank. This port takes the second option so that the record's tuned recipe applies unchanged; the gap left for entries is everything the record itself does not exploit on four GPUs, including the later short-track features (the 2025-12-31 record), which depend on a FlashAttention 3 kernel downloaded at run time and therefore cannot run in the offline sandbox as published.

3Method

3.1Model

16 blocks of width 1,024 with 8 heads of dimension 128; attention weights merged into one bf16 tensor per layer with a zero-initialised output projection; QK RMS normalisation and a fixed attention scale of 0.12. Layers 0–2 and 13–15 add value embeddings, layers 9–11 receive U-net skips from layers 6, 4 and 2, and every block mixes its input with the normalised token embedding through learned scalars. Layers 0, 4, 11 and 15 use the long window, all others half of it. The untied head has 50,304 rows and its logits are soft-capped by 15 · l / sqrt(l² + 225).

3.2Training on four GPUs

Each rank reads one flat 65,536-token sequence per micro-step from the training shards in order, exactly as the record's loader does, so two micro-steps on four ranks consume the same 524,288 tokens per step as the record's eight ranks. The loss of each micro-step is divided by the number of micro-steps; gradients are then all-reduced with averaging, the learning rate follows the record's schedule and Muon's momentum warms up from 0.85 to 0.95 over 300 steps. Ten warm-up steps on random tokens compile the kernels, after which model and optimizer states are restored. Rank 0 saves the uncompiled module's state dict.

3.3Evaluation interface

The evaluator calls model(idx) on consecutive windows of EVAL_SEQ_LEN = 32,768 tokens. Attention is masked to documents (token 50256 separates them), so a window boundary only removes context from the document it cuts; the record validates on 262,144-token sequences, and 32,768 keeps the fp32 logits of a window at 6.6 GB on one GPU.

4Design Rationale

A reference for a time-to-target case has to reach the target; the earlier AdamW reference had an uncalibrated step count and, judged against the track's 5.8-hour AdamW baseline on twice the GPUs, would very likely have missed it. Porting the public record keeps the reference honest about what is already known and makes the bar for entries explicit: valid submissions need speedrun-class methods, and improvements are measured against the record's recipe on the same four GPUs.

5Scope and Limitations

Not executed: neither the four-GPU port nor the evaluation interface has run (PyTorch and GPUs were not available where the case was built). The expected training time is about twice the record's 25 minutes plus compilation, but gradient accumulation adds memory traffic and two micro-steps of compiled autograd, so the real time and the final loss must be measured by the operator. The 140 extra steps are a guess at the margin needed, not a calibration. Everything in items 1–3 of the changes list is the record's work, not this submission's.
