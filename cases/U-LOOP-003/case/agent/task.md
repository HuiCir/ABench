# U-LOOP-003: Length generalisation on algorithmic tasks

Knowledge cutoff: **2026-07-01**. You may only rely on material that was public and verifiable before that date.

Anchor: Ying Fan, Yilun Du, Kannan Ramchandran, Kangwook Lee, *Looped Transformers for Length Generalization* (arXiv:2409.15647). Baseline used for comparison: a learned local lookup model (`interface/baseline/`).

## Task

Design an architecture and training procedure that learns three algorithmic tasks — **parity, binary addition and copy** — from examples of length 1–20 only, and **solves them exactly at lengths 21–40**. Develop and train it on one 24GB GPU in the sandbox, then submit the trained model.

- Submit your model code, the trained checkpoint and the training program that produced it. `train.py` must draw its training examples only from the provided sampler (lengths 1–20). The evaluator loads the checkpoint and answers held-out problems of lengths 1–40; it never retrains.
- The model must be learned from the sampled examples. Hand-written task algorithms, lookup of the answer by computation outside the learned model, or task-specific rules that encode the solution are not allowed; generic architectural choices (recurrence or looping, adaptive depth, position encodings, input formatting such as aligning operands) are the point of the task.
- You may build on any public work from before the cutoff (looped and universal transformers, adaptive computation, recurrent-depth models, position coupling), but the design report must state what you borrowed and what you changed.

5. **Submit** the deliverables below. Submission is one-shot.

## Data

There is no data file. Training data comes only from `interface/algo_tasks.py`: `Sampler(seed).sample(task, n, count)` returns `count` (input, output) pairs of length n ∈ 1..20 as int64 arrays.

| Task | Input | Output |
|---|---|---|
| `parity` | n bits | 1 token: XOR of the bits |
| `addition` | 2n bits: operand a then operand b, each least-significant bit first | n + 1 bits of a + b, LSB first |
| `copy` | n tokens from {0, …, 7}, repeats allowed | the same n tokens |

The held-out set has 50 problems per task and length for every length 1–40, generated by the same code with a secret seed; it is not in the sandbox. The self-check generates its own problems with a public seed.

## Interface

Implement `load(checkpoint_dir, device)` and `predict(model, task, inputs)` in `model.py`. `inputs` is a list of int64 arrays; `predict` returns a list of int arrays, the full output sequence for each input (its length counts). Your `train.py` writes `checkpoint/` from sampler examples.

The full reference is `interface/interface.md`. `abench_stage.py`, `stages.py` and `metrics.py` in `interface/` are the evaluator's own pipeline and metric code; `selfcheck.py` runs them on a dev split.

## Metrics

| Metric | Definition | Requirement |
|---|---|---|
| **OOD accuracy** (primary) | Exact-match accuracy (whole output sequence, including its length) on lengths 21–40, averaged over the 3 tasks; higher is better | — |
| Per-task OOD accuracy | The same for each task | reported |
| In-distribution accuracy | Exact-match accuracy on lengths 1–20, averaged over tasks | reported |
| Load time | Seconds from the start signal to the return of `load()` (includes importing `model.py`) | reported (killed at 120 s) |


No threshold applies to any metric: a submission is valid if it loads, runs within the time limits and returns well-formed outputs (see below).
**Timing and decision**

- Loading and prediction run in a new process with empty cache directories, on the same GPU model, timed by the evaluator's parent process (`interface/abench_stage.py`). `predict()` runs after the timed phase; all 6,000 problems must be answered within 300 seconds.
- A submission is valid only if the code follows the learning rule above (checked by inspecting `model.py` and `train.py`); valid submissions are ranked by OOD accuracy.
- If loading or prediction crashes, exceeds a time limit, or returns the wrong number of outputs, the submission is invalid.
- The final ABench score is driven mainly by OOD accuracy, and also considers how different the method is from existing methods and the quality of the sources cited in the design report; the exact weights are not published.

## Evaluation

1. When your session ends, the sandbox collects only the allowed files from `ABENCH_SUBMISSION_DIR`; the workspace is deleted.
2. The evaluator runs outside the sandbox: it checks the submission format, then loads your submitted checkpoint with your model code and runs inference through the stages in `interface/stages.py`, once, on the evaluation hardware; it never retrains your model and never runs `train.py`.
3. Held-out inputs are copied into the run directory only after the timed phase has ended, and never with their labels or reference values; those stay in the evaluator process, which computes the metrics with `interface/metrics.py`.
4. You receive no evaluation results during your session.

## Rules

- The checkpoint must be produced by your `train.py` from the provided data only, inside the sandbox; no pretrained weights, no external data and no hand-set parameters copied from elsewhere.
- The evaluator loads `checkpoint/` with your model code and runs inference only; it does not run `train.py`, which is kept for audit and must reproduce the checkpoint up to randomness.
- Training data only from the provided sampler, in `train.py`; no pretrained weights.
- No hand-written solution of a task anywhere in the submission (for example computing XOR, sums or copies directly, or a lookup that encodes the rule); the prediction must come from the learned model.
- Do not read or write files outside the submission directory, the run directory and the paths the stage gives you; do not access the network; do not touch the timing pipe or the protocol bytes.
- Do not use extra processes or background threads to move work outside the timed phase, and do not leave processes running after a stage returns.
- Submission is one-shot. A submission that breaks the rules is invalid.
