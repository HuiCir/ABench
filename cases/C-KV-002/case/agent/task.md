# C-KV-002: Key-value cache compression for Qwen2.5-1.5B at three memory budgets: long-context retrieval up to 16k tokens

Anchor: Zirui Liu, Jiayi Yuan, Hongye Jin, Shaochen Zhong, Zhaozhuo Xu, Vladimir Braverman, Beidi Chen, Xia Hu, *KIVI: A Tuning-Free Asymmetric 2bit Quantization for KV Cache* (arXiv:2402.02750). Baseline used for comparison: per-token asymmetric 4-, 2- and 1-bit quantisation of keys and values (a simplified KIVI; the reference submission, its code shown under `interface/baseline/`); the uncompressed cache is evaluated alongside as the ceiling.

## Task

Design a **key-value cache compression scheme** — quantisation, eviction, merging, low-rank projection or a mix — that keeps Qwen2.5-1.5B-Instruct's **long-context retrieval accuracy** as high as possible when the cache may store at most **4.5, 2.5 or 2.0 bits per cached element** (against 16 for bf16), on prompts of 4k, 8k and 16k tokens.

- Submit the cache only (`cache.py` with `make_cache(budget_bits, config)`, returning a transformers cache object). The evaluator owns the model and the decoding loop: it prefills each prompt into your cache, counts the bytes of every tensor your cache object holds, then decodes 32 tokens greedily with it.
- A prompt whose stored cache exceeds the budget scores 0 at that budget; the budget is measured per prompt, so it must hold at 4k as well as at 16k tokens.
- Tasks in the style of RULER: one or several "magic numbers" hidden in long noise text, several values for one key, and variable tracking through a chain of assignments; 12 prompts per task and length.
- You may build on any public work (cache quantisation, token eviction and selection, merging, attention-sink retention, low-rank keys), but the design report must state what you borrowed and what you changed.

## Data

`$ABENCH_DATA_DIR/dev_prompts.npz` (read-only): 36 development prompts (3 per task and length), generated with a public seed by `interface/ruler_tasks.py` and tokenised like the held-out ones: `tokens` / `offsets` (prompt i is `tokens[offsets[i]:offsets[i+1]]`, chat template and answer prefix included), `task`, `length`, `expected` (expected strings joined by `|`). `$ABENCH_MODELS_DIR/Qwen2.5-1.5B-Instruct` (Apache-2.0).

The 144 held-out prompts are generated by the same code with a secret seed; they are not in the sandbox. You can generate as many more as you like with `ruler_tasks.make`.

## Interface

Implement `make_cache(budget_bits, config) -> cache` in `cache.py`, where `budget_bits` is 4.5, 2.5 or 2.0 and `config` the model's transformers config; the cache must be a `transformers` cache object usable as `past_key_values` (its `update(key_states, value_states, layer_idx, cache_kwargs)` receives the new keys and values and returns those the attention should use). A new cache is made for every prompt.

The full reference is `interface/interface.md`. `abench_stage.py`, `stages.py` and `metrics.py` in `interface/` are the evaluator's own pipeline and metric code; `selfcheck.py` runs them on a dev split.

## Metrics

| Metric | Definition | Requirement |
|---|---|---|
| **Mean budget score** (primary) | RULER string-match score (fraction of expected strings in the answer), averaged over the 144 held-out prompts at each budget, then over the three budgets; a prompt over its budget scores 0; higher is better | — |
| Score per budget | At 4.5, 2.5 and 2.0 bits | reported |
| Uncompressed score | The same prompts with transformers' DynamicCache (bf16) | reported |
| Score by task and length | Per budget | reported |
| Stored bits | Largest stored bits per element over prompts, per budget, and the fraction of prompts within budget | reported |

No threshold applies to any metric: a prompt over budget simply scores 0, and a submission is valid if it loads, runs within the time limits and the code follows the rules (see below).

**Measurement and decision**

- Stored bits per element = 8 × (bytes of all tensors reachable from the cache object after the prefill) / (tokens × 28 layers × 2 key-value heads × 128 × 2).
- Everything runs in one new process on the reference GPU, timed by the evaluator's parent process (`interface/abench_stage.py`); importing `cache.py` is killed at 120 s and the whole evaluation (four passes over 144 prompts) must finish within 2,700 seconds.
- Valid submissions are ranked by mean budget score. Differences below 0.02 (about three prompts per budget) are treated as ties.
- The final ABench score is driven mainly by the mean budget score, and also considers how different the scheme is from existing ones and the quality of the sources cited in the design report; the exact weights are not published.

## Evaluation

1. When your session ends, the sandbox collects only the allowed files from `ABENCH_SUBMISSION_DIR`; the workspace is deleted.
2. The evaluator runs outside the sandbox: it checks the submission format, then loads your submitted checkpoint with your model code and runs inference through the stages in `interface/stages.py`, once, on the evaluation hardware; it never retrains your model to evaluate it (`train.py` is only re-run in the audit below).
3. Held-out inputs are copied into the run directory only after the timed phase has ended, and never with their labels or reference values; those stay in the evaluator process, which computes the metrics with `interface/metrics.py`.
4. Audit: the operator re-runs your `train.py` from scratch for the top-ranked submissions and for a random sample of the others. If the re-trained checkpoint's primary metric falls outside your submitted checkpoint's 95% interval, widened by the run-to-run spread the operator measures for the reference `train.py`, the submission is invalid.
5. You receive no evaluation results during your session.

## Rules

- The cache must hold everything needed to continue decoding in tensors reachable from the cache object; nothing may be kept elsewhere (module globals, files, other objects) across `update` calls.
- The cache may only depend on the keys and values it receives and on calibration data in `checkpoint/` produced by `train.py` from the provided model and generated text; it must not read the prompts' text or detect the task.
- Do not read or write files outside the submission directory, the run directory and the paths the stage gives you; do not access the network; do not touch the timing pipe or the protocol bytes.
- Do not use extra processes or background threads to move work outside the timed phase, and do not leave processes running after a stage returns.
- Submission is one-shot. A submission that breaks the rules is invalid.
