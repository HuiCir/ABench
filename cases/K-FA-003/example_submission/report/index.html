Blockwise Attention with an Online Softmax in Plain PyTorch

ABench reference submissionStandard reference for task statement standard v2.1
Abstract

This submission gives the algorithmic skeleton of FlashAttention without a fused kernel. Queries are processed in blocks of 256 and keys and values are streamed in blocks of 256; a running row maximum and normaliser implement the online softmax (Milakov & Gimelshein, 2018), so the softmax is exact while the T × T score matrix is never materialised (Dao et al., 2022; Rabe & Staats, 2021). Each block is computed with ordinary PyTorch operations in fp32, so the result is accurate but every block round-trips through device memory; fusing the loop into one kernel, as the anchor does, is what entries are expected to do.

1Introduction

Attention is limited by memory traffic rather than arithmetic for typical sequence lengths: the naive algorithm writes and reads the full score matrix. FlashAttention tiles the computation so that scores live only in on-chip memory (Dao et al., 2022). The same tiling expressed with tensor operations keeps memory linear in the sequence length but not the traffic, which makes the gap between algorithm and kernel visible.

Changes relative to the anchor. Each item states what this submission does differently and where it is in the code.

  2. Computation inside each block is in fp32. — kernel.py: attention

2Related Work

The online softmax maintains, for each query row, the maximum m and the sum l of exponentials seen so far, and rescales the partial output when m grows (Milakov & Gimelshein, 2018). Memory-efficient attention applies this to blocks of keys (Rabe & Staats, 2021); FlashAttention fuses it with the matrix products in a single kernel and reorders the loops for parallelism (Dao et al., 2022; Dao, 2023).

FlashAttention fuses the tiled online softmax into one kernel; memory-efficient tensor-level tilings keep memory linear but not the traffic; the fused kernel is the gap.

3Method

3.1Algorithm

For each query block Q_b (scaled by 1/sqrt(D)), m ← −∞, l ← 0, A ← 0. For each key block with keys K_c and values V_c (only blocks up to the diagonal when causal): S ← Q_b K_cᵀ with masked entries set to −∞, m' ← max(m, rowmax S), P ← exp(S − m'), l ← l·exp(m − m') + rowsum P, A ← A·exp(m − m') + P V_c, m ← m'. The output block is A / l cast to bf16.

3.2Complexity

Arithmetic is O(B H T² D) as for any exact attention (halved when causal). Extra memory is O(B H · 256 · 256) for one score block instead of O(B H T²). Memory traffic is still O(B H T² ) because each block of scores is written and read by separate operations.

4Design Rationale

Computing in fp32 and casting once at the end keeps the error well inside the bounds set by SDPA's own bf16 error. Skipping key blocks above the diagonal halves the work of causal attention. Block sizes of 256 keep the number of Python-level iterations small for the longest sequences.

5Scope and Limitations

Each operation is a separate kernel launch, so the implementation is memory-bound and slower than SDPA. A fused Triton or CUDA kernel with on-chip tiles, tuned block sizes per head dimension and parallelism over query blocks is required to compete.
