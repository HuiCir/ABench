It tests architecture design,not paper reproduction

ABench asks an agent to start from a classic paper, research the literature throughout its session (the sandbox is online for papers and code; dataset and model hubs are blocked), synthesize it, and design an architecture that is better than and different from existing ones. Evaluation works like an online judge: the agent gets only the task statement, interface and public training data, and submits code, weights and a design report that explains only principles; the test set stays outside the sandbox, the judge loads the submission to compute metrics, and the overall score combines SOTA margin, method divergence, reference quality and local discovery.

    OJ evaluation: the test set never enters the sandbox

    The agent view is built from an allowlist: task statement, interface, report templates and public training data, all read-only. Hidden settings, reference methods and scoring weights are not in it. Only after the agent finishes and the workspace is deleted does the judge decrypt the hidden set and load the submission: model code and the checkpoint the agent trained, or, where the training program itself is measured, the code it trains from scratch.

        Standard cases: the agent trains, the evaluator only evaluates

        Every track has at least one standard case built to task statement v2.1. The agent gets compute in the sandbox to explore, train and check its own work with the evaluator's own pipeline; what the evaluator then does depends on what the case measures.

        Workflow required by every standard task statement

          Research is not a phase: the agent returns to the literature whenever training raises a question. The sandbox is online for papers, code and documentation through the runner's logging proxy, and the offline paper search answers fast from CC0 arXiv metadata; both are logged with the run. A design report without the list <ol id="changes">, or with a change that has no code location, fails the format check.

            Evaluation modes: three thresholds, four components

            All scoring happens outside the sandbox. The task statement publishes the metrics, thresholds and score components, but not the weights or the reference pool. The three submissions of one case go through the same scoring; switch between them to see where each scores and where it is stopped.

            SOTA margin M: effective speedup against the reference envelope

            Divergence D: behavioral similarity on a fixed gradient stream

            Reference quality Q: paper weight × usage

            Local discovery X: per-claim ablation

            Only the training losses and judge outputs in the historical demo of B-OPT-001 are simulated; no results were generated for the new cases, and formal scoring must use a real runner.

            x = effectiveness · application novelty · provenance correctness · (0.5 + 0.5 · provenance distance)

            X = 1 − Π(1 − x) overall × (1 + 0.25 · X)

            Effectiveness comes from the benchmark operator's ablation: replace the module with a trivial substitute and retrain; the drop in gain must exceed seed noise. Venue tier and citations of cross-field sources are assessed within their own fields.

            Three verification modes, three resource tiers, three difficulty levels

            Agents need repeated trial and error, so the Budget edition never trains at the paper's full or large scale; the compute-heavy industrial tasks form a separate Pro Set with ample compute, verified by audit instead.

            Budget: micro-scale ladder

            One 24GB reference card. The benchmark operator retrains the agent's method at μ1–μ3, and hidden settings are not available to the agent.

            Pro: audit instead of retraining

            4 × H100, 24 hours. Checkpoint hashes are registered every 30 minutes, and the benchmark operator resumes from one randomly chosen registered point for 1 hour to check.

            Strong baselines at equal compute

            Published gains often vanish against a tuned baseline. Design cases therefore compare every submission with a tuned mainstream baseline trained or fitted by the evaluator at the same budget.
